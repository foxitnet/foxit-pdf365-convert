# API Key 管理（必须首先执行）

> 📌 本文档独立维护 PDF365 的 API Key 相关流程。SKILL.md 中的「API Key 管理」章节即指向本文，调用 Skill 时完整遵循本文件内容。

调用本 Skill 的**第一步**必须检查本地是否已存在 API Key。

> 💾 **Key 存储位置（重要）**：API Key 保存在**当前 Skill 目录内**的 `skill_key` 文件中（即 `<skill目录>/skill_key`，与 `SKILL.md` 同级），随技能一起管理，而不是存放在全局 `~/.pdf365/` 目录。
>
> 由于每个 AI 平台（如 VS Code/Copilot、WorkBuddy、qclaw、Claude Code 等）**独立安装一份该 Skill**、各自拥有独立的技能目录，因此各平台之间的 `skill_key` 天然隔离、互不覆盖。各平台账号不同也互不影响，从根本上避免多平台 Key 互相覆盖导致的混乱或失效。


## 检查流程

1. **读取本地 Key**：检查本技能目录下 `skill_key` 文件是否存在且内容非空
   - 文件路径：`<skill目录>/skill_key`（即 `foxit-pdf365-convert/skill_key`）
2. **Key 存在**：读取文件内容作为 `X-API-KEY`，继续后续流程
3. **Key 不存在**：
   - 提示用户："尚未检测到 PDF365 API Key。请前往 https://www.pdf365.cn/skill_key 创建 Key，然后将 Key 复制粘贴给我。"
   - **等待用户回复 Key 值**
    - 收到 Key 后，将用户提供的 Key **原样完整写入**本技能目录下的 `skill_key` 文件（若文件不存在则创建）
   - **同步生成 `.gitignore`（首次写入必须执行）**：技能目录内**不默认存在** `.gitignore`。检查是否存在：
     - **不存在** → 创建 `.gitignore` 文件，并写入忽略规则 `skill_key`
     - **已存在但未包含 `skill_key`** → 在文件末尾**追加**一行为`skill_key`
     - **已包含 `skill_key` 规则** → 无需修改
     确保 `skill_key` 被加入忽略，**不被提交进版本库**
   - 提示用户："API Key 已保存到本地，后续无需重复配置。"
   - 继续后续流程

> ⚠️ `.gitignore` **不默认存在**：首次写入 `skill_key` 时**必须同步生成/补齐 `.gitignore`** 并包含 `skill_key` 忽略规则（见上文步骤 3），确保 `skill_key` 不进版本库、避免密钥泄漏。

> ⚠ **Key 完整性（极其重要）**：用户提供的 Key 格式为 `PDF365-MCP-xxxxxxxx`，其中 `PDF365-MCP-` 是 Key 不可分割的一部分，**不是**命名空间、标签或可省略的前缀。存储和使用时必须保留完整字符串，不得截断、去除或忽略 `PDF365-MCP-` 前缀。写入本地文件和 MCP 配置时，值必须是用户粘贴的原始完整内容。

> 🔧 **读取 Key 时去除 BOM 与空白（极其重要）**：本技能目录内的 `skill_key` 文件可能被编辑器以 **UTF-8 BOM** 编码保存（文件首字节为 `EF BB BF`）。若直接以 UTF-8 解码，读取出的 Key 会带有不可见的 `\ufeff`（BOM）前缀；若文件含首尾空白或换行，同样会导致 Key 不干净。用带前缀的 Key 发起 HTTP 上传时会触发 `UnicodeEncodeError`。或造成鉴权失败，上传流程直接崩溃。
>
> 因此，**任何**从本地文件读取 Key 的操作（作为 `X-API-KEY`、写入 MCP 配置 `headers["X-API-KEY"]`、curl `-H "X-API-KEY: ${API_KEY}"`）都必须：
>
> 1. **以 BOM 感知方式解码**：Python 使用 `open(path, encoding='utf-8-sig').read()`（`utf-8-sig` 会自动剔除开头 BOM），或在字符串上调用 `.lstrip('\ufeff')` 去除 `\ufeff` 前缀。
> 2. **去除首尾空白**：对读取结果执行 `.strip()`，剔除首尾空格、`\n`、`\r`、`\t` 等。
> 3. **处理顺序**：先去 BOM，再 `strip()`（`('utf-8-sig').read().strip()`）。
> 4. 清洗后的 Key 仍是完整的 `PDF365-MCP-xxxxxxxx`，不得在去 BOM/空白过程中误删该前缀。

## 运维安全约束（必须遵守）

> ⚠️ 本技能要求 **Key 最小暴露、最小权限、可轮换、可撤销**，且**绝不允许**出现在日志、错误堆栈、命令历史或安装包中。以下约束适用于 `skill_key` 文件与所有写入 `X-API-KEY` 的 MCP 配置文件（见 [MCP.md](./MCP.md)）。

### 1. 最小暴露与最小权限

- **副本最小化**：Key 仅允许存在于**本机**的两处——① 技能目录内 `skill_key` 文件；② 真正需要使用 PDF365 的当前客户端 MCP 配置 `headers["X-API-KEY"]`。
- **禁止扩散**：不得将 Key 复制到任何笔记、便签、文档、聊天、剪贴板驻留或其他配置文件；剪贴板使用后应清除，防止被其他进程读取。
- **多客户端节制**：每个客户端一份明文副本就是多一份泄漏面与轮换成本。**仅为确实在用的客户端**写入 MCP 配置；未使用、已停用或已卸载的客户端，不得再为其复制 Key。
- **用途受限**：Key 仅用于本转换接口的鉴权，不用于任何其他用途；避免在公共 / 共享机器长期保存 Key。

### 2. 文件访问权限（ACL）

- **Unix / Linux / macOS**：设置 `skill_key` 及含 Key 的 MCP 配置文件权限为仅当前用户可读写：`chmod 600 <文件>`。
- **Windows**：通过「属性 → 安全」收紧 `skill_key` 与 MCP 配置文件的 ACL，**移除其他用户 / 组的读取权限**（如 Everyone、Users），仅保留当前账户。
- 收紧权限后再写入 Key；本次会话中如有漏配，应立即修正。

### 3. 备份 / 同步 / 安装包排除

- 首次写入 `skill_key` 时应**同步生成/补齐 `.gitignore`**（见上文「检查流程」步骤 3），确保 `skill_key` 不进版本库；此外还必须将 `skill_key` 及含 Key 的 MCP 配置文件**排除出**一切**云盘同步、自动备份、镜像、安装 / 部署 / 分发包**（如 `.zip`、`.tar`、离线目录打包）。
- 分发技能或 MCP 配置时，`X-API-KEY` 一律使用占位符 `YOUR_API_KEY`，**不得包含真实 Key**。
- 已确认曾将含真实 Key 的文件打入备份 / 同步 / 安装包，视同泄漏，**立即执行第 6 节「泄漏撤销」**轮换。

### 4. 日志脱敏与命令历史保护

- **日志脱敏**：读取、写入、上传、转换、下载全过程中，任何打印 / 日志 / 错误提示**不得输出完整 Key 及完整的 `X-API-KEY` 请求头**。确需输出时仅显示脱敏形式（如 `PDF365-MCP-****xxxx`）。
- **错误堆栈**：捕获异常时**不得把 Key 或含 Key 的请求对象原样拼入堆栈 / 报错信息**返回给用户或写入日志，一律脱敏后再展示。
- **命令历史保护**：**严禁**在命令行中以明文书写 Key（如 `-H "X-API-KEY: PDF365-MCP-xxxx"`，会写入 shell / PowerShell 历史）。必须先将 Key 注入环境变量（例如 `export API_KEY=$(cat "<skill目录>/skill_key")`，该命令本身不含明文 Key），后续全部以 `$API_KEY` 引用；并检查 `~/.bash_history`、`~/.zsh_history`、PowerShell `PSReadLine` 历史中**不得残留明文 Key**。

### 5. 轮换（Rotation）

- Key 应定期 / 触发式轮换，触发条件包括：疑似或确认泄漏、提交进代码库、被打包 / 同步 / 分发、长期不用后重新启用、账号或权限变更。
- 轮换执行「切换账号 / 替换 Key」流程（下文）：创建新 Key → 替换本地 `skill_key` 与 MCP 配置两处 → 重载 MCP → 在控制台作废旧 Key。

### 6. 泄漏撤销（Revocation）

- **检测到 / 确认泄漏**时，**立即**前往 https://www.pdf365.cn/skill_key **撤销（吊销）**该 Key，并创建新 Key 按「替换 Key」流程替换两处。
- 撤销后旧 Key 立即失效，使用旧 Key 的请求会返回鉴权失败（HTTP 401 / `invalid key` 等），按「Key 无效处理」统一引导更新。
- 泄漏处理后，**排查并记录泄漏渠道**（日志、命令历史、备份 / 同步、安装包、共享目录、剪贴板、代码库），针对渠道封堵，防止复发。
- **原则**：宁可立即轮换，也绝不猜测泄漏风险是否可控。

### 切换账号 / 替换 Key

当用户表达想要**切换账号**或**更换 API Key**时，按以下流程处理：

1. **引导创建新 Key**：提示用户："如需切换账号，请前往 https://www.pdf365.cn/skill_key 创建新的 Key，然后将新 Key 复制粘贴给我。"
2. **等待用户粘贴新 Key**：收到用户粘贴回来的新 Key 值
3. **二次确认（必须执行）**：明确提醒用户"该操作将**替换当前已保存的 Key**，替换后原账号将无法继续使用，确认替换吗？"，**等待用户确认**
4. **用户确认后执行替换**：
   - 将新 Key **原样完整写入**本技能目录下的 `skill_key`，覆盖原有内容（必须包含 `PDF365-MCP-` 前缀，不得截断）
   - **同步替换 MCP 配置中的 `X-API-KEY`**：定位当前客户端的 MCP 配置文件（见「MCP 配置」各客户端路径），将 `foxit-pdf365-mcp-server` 节点下 `headers["X-API-KEY"]` 的值替换为完整的新 Key（含 `PDF365-MCP-` 前缀），保留其他配置不变
   - 提示用户："API Key 已替换，请重载 MCP 使新配置生效。"
5. **用户未确认**：不执行任何替换操作，保持原 Key 不变

> ⚠️ 替换 Key 前必须经过用户二次确认，未确认不得覆盖本地 Key 或修改 MCP 配置。
> ⚠️ 替换本地 Key 时必须同步更新 MCP 配置中的 `X-API-KEY`，确保两处一致。

> ⚠️ 所有 MCP 工具调用和上传接口请求都必须携带 `X-API-KEY` 请求头，值为本地存储的**完整** Key（含 `PDF365-MCP-` 前缀）。
>
> ⚠️ 部分平台在存储 Key 时可能误将 `PDF365-MCP-` 当作命名空间前缀而截断。写入 Key 后应验证文件内容与用户提供的原始值完全一致，若发现前缀丢失须重新写入完整 Key。

### Key 无效处理

当上传接口或任一 MCP 工具（`createConvertTask`、`getConvertTaskStatus`、`downloadConvertResult`）返回 **Key 无效 / 鉴权失败**（如 HTTP 401、报错包含 `invalid key`、`unauthorized`、`API Key 校验失败` 等）时，执行以下流程：

1. **识别 Key 无效**：发现 Key 无效后，**立即停止**当前上传/转换/下载流程，不得继续重试。
2. **提示用户重新获取 Key**：明确告知用户："当前 API Key 已失效，请前往 https://www.pdf365.cn/skill_key 重新创建新的 API Key，然后将新 Key 复制粘贴给我。"
3. **等待用户提供新 Key**：收到新 Key 后，将新 Key **原样完整写入**本技能目录下的 `skill_key`，覆盖原失效 Key（必须包含 `PDF365-MCP-` 前缀，不得截断）。
4. **同步更新 MCP 配置**：同步替换当前客户端 MCP 配置文件（见「MCP 配置」各客户端路径）中 `foxit-pdf365-mcp-server` 节点下 `headers["X-API-KEY"]` 的值为新 Key，确保本地与 MCP 两处一致。
5. **提示重载 MCP**：提示用户"API Key 已更新，请重载 MCP 使新配置生效。"
6. **继续流程**：从**上传接口**重新开始执行（步骤见「转换执行约定」→「执行流程」步骤 1）。
7. **反复无效**：若用户提供的新 Key 依旧无效，提示用户确认是否为最新 Key，必要时引导重新创建；若用户拒绝，则结束流程。

> ⚠️ **不得沿用失效 Key**：发现 Key 无效时严禁尝试通过旧 Key 重试或绕过鉴权，必须以用户重新提供的 Key 为准进行覆盖更新。
> ⚠️ 更新 Key 时本地文件与 MCP 配置两处必须同步更新，保持一致。
